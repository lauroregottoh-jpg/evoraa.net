# 04 --- MOTEUR DE MATCHING ET DE SCORING

# KELYA COUPLE™

## Architecture méthodologique du questionnaire, des scores, du matching et de l'interprétation

**Document maître pour le moteur d'analyse relationnelle**

------------------------------------------------------------------------

# 1. OBJECTIF DU DOCUMENT

Ce document définit la logique méthodologique du moteur KELYA COUPLE™.

Il précise :

-   ce que le questionnaire doit mesurer ;
-   comment les réponses sont transformées en scores ;
-   comment les profils individuels sont construits ;
-   comment les deux profils sont comparés ;
-   comment le système distingue convergence, différence et zone de
    vigilance ;
-   comment le score global doit être interprété ;
-   comment éviter qu'un faible pourcentage soit présenté comme une
    condamnation du couple ;
-   comment les résultats alimentent le rapport ;
-   comment les règles de sécurité méthodologique doivent être
    appliquées.

Ce document ne constitue pas un diagnostic clinique.

KELYA COUPLE produit un **bilan relationnel structuré**, destiné à
favoriser la compréhension, la conversation et le travail relationnel.

------------------------------------------------------------------------

# 2. PRINCIPE FONDAMENTAL

Le moteur ne doit jamais réduire la relation à un seul nombre.

Le score global est une synthèse.

Le véritable résultat est constitué de plusieurs niveaux :

``` text
RÉPONSES INDIVIDUELLES
        ↓
PROFILS INDIVIDUELS
        ↓
DIMENSIONS RELATIONNELLES
        ↓
CONVERGENCES
        ↓
DIFFÉRENCES
        ↓
ZONES DE VIGILANCE
        ↓
RESSOURCES DU COUPLE
        ↓
PRIORITÉS DE TRAVAIL
        ↓
SYNTHÈSE GLOBALE
```

Le moteur doit donc être multidimensionnel.

------------------------------------------------------------------------

# 3. CE QUE LE MOTEUR DOIT MESURER

La structure définitive du questionnaire sera précisée dans le document
dédié aux questions, mais le moteur doit être conçu pour pouvoir mesurer
au minimum les grands domaines suivants.

## 3.1 Communication

Capacité à exprimer :

-   besoins ;
-   attentes ;
-   désaccords ;
-   émotions ;
-   demandes ;
-   limites.

------------------------------------------------------------------------

## 3.2 Gestion des conflits

Le moteur cherche notamment à comprendre :

-   comment chacun réagit au désaccord ;
-   tendance à éviter ;
-   tendance à attaquer ;
-   tendance à se fermer ;
-   capacité à réparer ;
-   capacité à reprendre une conversation difficile.

------------------------------------------------------------------------

## 3.3 Valeurs

Comparer la proximité autour de sujets structurants :

-   famille ;
-   fidélité ;
-   engagement ;
-   respect ;
-   responsabilité ;
-   spiritualité ou religion lorsque cette dimension est volontairement
    incluse ;
-   vision du couple ;
-   principes de vie.

------------------------------------------------------------------------

## 3.4 Projet de vie

Cette dimension peut comprendre :

-   mariage ;
-   lieu de vie ;
-   carrière ;
-   mobilité ;
-   niveau de vie ;
-   projets personnels ;
-   rythme de vie ;
-   priorités futures.

------------------------------------------------------------------------

## 3.5 Projet familial

Cette dimension peut explorer :

-   désir d'enfant ;
-   nombre d'enfants souhaité ;
-   calendrier ;
-   rôle parental ;
-   éducation ;
-   organisation familiale.

------------------------------------------------------------------------

## 3.6 Finances

Explorer notamment :

-   rapport à l'argent ;
-   épargne ;
-   dépenses ;
-   gestion commune ;
-   autonomie financière ;
-   responsabilités ;
-   transparence.

------------------------------------------------------------------------

## 3.7 Intimité et affection

Cette dimension doit rester formulée avec tact.

Elle peut couvrir :

-   expression de l'affection ;
-   besoin de proximité ;
-   besoin d'espace ;
-   sentiment de sécurité ;
-   importance accordée à l'intimité ;
-   capacité à parler des besoins.

------------------------------------------------------------------------

## 3.8 Familles et entourage

Explorer :

-   place des familles ;
-   limites ;
-   influence extérieure ;
-   disponibilité ;
-   décisions prises avec ou sans entourage ;
-   protection de l'espace du couple.

------------------------------------------------------------------------

## 3.9 Rôles et responsabilités

Comparer les attentes concernant :

-   tâches ;
-   responsabilités ;
-   organisation ;
-   charge mentale ;
-   décisions ;
-   contribution financière ;
-   responsabilités familiales.

------------------------------------------------------------------------

## 3.10 Autonomie et espace personnel

Explorer :

-   besoin d'indépendance ;
-   besoin de proximité ;
-   activités personnelles ;
-   temps seul ;
-   amitiés ;
-   équilibre entre « moi » et « nous ».

------------------------------------------------------------------------

## 3.11 Sécurité émotionnelle

Explorer :

-   confiance ;
-   sentiment d'être entendu ;
-   sentiment d'être respecté ;
-   possibilité d'être vulnérable ;
-   peur du rejet ;
-   sécurité dans les désaccords.

------------------------------------------------------------------------

## 3.12 Engagement

Explorer :

-   vision de la relation ;
-   niveau d'engagement ;
-   volonté de construire ;
-   projection ;
-   constance ;
-   responsabilité relationnelle.

------------------------------------------------------------------------

# 4. INDIVIDUEL ET COUPLE

Chaque dimension doit produire au minimum trois informations :

``` text
SCORE A
SCORE B
ÉCART A/B
```

Mais le moteur doit également déterminer :

``` text
NIVEAU A
NIVEAU B
CONVERGENCE
DIVERGENCE
NIVEAU DE VIGILANCE
```

Exemple :

``` text
Communication

A = 82
B = 79
Écart = 3

→ Forte convergence
→ Ressource du couple
→ Faible vigilance
```

Autre exemple :

``` text
Communication

A = 86
B = 48
Écart = 38

→ Forte divergence
→ Sujet important
→ Vigilance élevée
```

------------------------------------------------------------------------

# 5. LE SCORE INDIVIDUEL

Chaque dimension doit produire un score normalisé sur 100.

Exemple :

``` text
Communication = 78/100
Conflits = 61/100
Finances = 42/100
Projet familial = 88/100
```

Le score ne signifie pas :

> « 78 % de réussite. »

Il représente le niveau observé sur la dimension selon les règles du
questionnaire.

Les textes doivent toujours expliquer ce que le score représente.

------------------------------------------------------------------------

# 6. NORMALISATION

Les dimensions peuvent contenir un nombre différent de questions.

Le moteur doit donc normaliser les résultats.

Principe :

``` text
Score brut
    ↓
Transformation
    ↓
Normalisation
    ↓
Score /100
```

Les différentes dimensions doivent être comparables sans être
artificiellement identiques.

------------------------------------------------------------------------

# 7. QUESTIONS À SENS INVERSÉ

Certaines questions peuvent être formulées dans un sens opposé.

Exemple :

> « Lorsque nous sommes en désaccord, je préfère éviter la conversation.
> »

Une réponse élevée ne doit pas être interprétée comme une meilleure
capacité de gestion des conflits.

Le moteur doit donc prévoir :

``` text
QUESTION_NORMAL
QUESTION_INVERSE
```

Pour une question inversée :

``` text
Score interprété = maximum - score brut
```

La formule exacte dépendra de l'échelle retenue.

------------------------------------------------------------------------

# 8. ÉCHELLE DE RÉPONSE

Une échelle de type Likert peut être utilisée.

Exemple :

``` text
1 — Pas du tout vrai pour moi
2 — Plutôt faux
3 — Mitigé
4 — Plutôt vrai
5 — Tout à fait vrai pour moi
```

Le questionnaire doit rester cohérent sur toute sa longueur.

Les changements d'échelle doivent être exceptionnels et justifiés.

------------------------------------------------------------------------

# 9. QUESTIONS DE CONTRÔLE

Le questionnaire peut contenir des éléments destinés à vérifier la
cohérence des réponses.

Le moteur peut détecter :

-   réponses systématiquement extrêmes ;
-   contradictions importantes ;
-   temps de réponse anormalement court ;
-   répétitions mécaniques ;
-   patterns incohérents.

Ces éléments doivent servir principalement à **contrôler la qualité des
données**.

Ils ne doivent pas être présentés comme un jugement sur la personne.

------------------------------------------------------------------------

# 10. QUALITÉ DE RÉPONSE

Le moteur doit pouvoir calculer un indicateur interne :

``` text
DATA_QUALITY
```

Exemple :

``` text
HIGH
MEDIUM
LOW
```

Si la qualité des réponses est insuffisante, le système peut :

-   demander une vérification ;
-   demander de compléter certaines réponses ;
-   limiter certaines interprétations ;
-   afficher une mention de prudence dans le rapport.

------------------------------------------------------------------------

# 11. ÉCART ENTRE PARTENAIRES

Pour chaque dimension :

``` text
Écart = ABS(score_A - score_B)
```

Exemple :

``` text
A = 75
B = 65

Écart = 10
```

Mais l'écart seul ne suffit pas.

Il faut également connaître **la nature des deux scores**.

------------------------------------------------------------------------

# 12. POURQUOI L'ÉCART SEUL NE SUFFIT PAS

Comparer :

``` text
A = 90
B = 80
```

et :

``` text
A = 40
B = 30
```

donne dans les deux cas :

``` text
Écart = 10
```

Pourtant la signification relationnelle peut être différente.

Dans le premier cas, les deux personnes peuvent disposer d'une ressource
solide.

Dans le second cas, les deux personnes peuvent avoir besoin de
travailler le domaine.

Le moteur doit donc analyser :

``` text
niveau individuel
+
écart
+
importance de la dimension
+
cohérence avec les autres résultats
```

------------------------------------------------------------------------

# 13. CONVERGENCE

Une convergence signifie que les deux partenaires présentent des niveaux
proches sur une dimension.

Mais une convergence peut être :

### Convergence forte positive

Les deux ont un niveau élevé.

### Convergence modérée

Les deux sont relativement proches.

### Convergence faible

Les deux sont proches mais dans une zone basse.

Cette distinction est essentielle.

------------------------------------------------------------------------

# 14. DIVERGENCE

Une divergence signifie que les deux partenaires présentent des niveaux
sensiblement différents.

La divergence n'est pas automatiquement négative.

Elle peut représenter :

-   une complémentarité ;
-   une différence de besoin ;
-   une différence de style ;
-   une source potentielle de tension ;
-   un sujet à négocier.

Le moteur doit déterminer laquelle de ces interprétations est la plus
pertinente.

------------------------------------------------------------------------

# 15. COMPLÉMENTARITÉ

Certaines différences peuvent être fonctionnelles.

Exemple :

> Une personne est très organisée et l'autre plus flexible.

Ce n'est pas nécessairement un problème.

Le moteur doit rechercher si les deux styles :

-   se complètent ;
-   se neutralisent ;
-   créent de la tension ;
-   nécessitent un accord explicite.

Il ne faut jamais convertir automatiquement :

``` text
DIFFÉRENCE = PROBLÈME
```

------------------------------------------------------------------------

# 16. ZONE DE VIGILANCE

Une zone de vigilance doit apparaître lorsqu'une combinaison de facteurs
indique qu'un sujet mérite une attention particulière.

Exemple :

``` text
Écart élevé
+
dimension importante
+
score faible d'au moins un partenaire
=
vigilance renforcée
```

Le moteur peut classer les niveaux :

``` text
Faible
Modérée
Importante
Élevée
```

Mais les mots employés dans le rapport doivent rester nuancés.

------------------------------------------------------------------------

# 17. PRIORISATION

Toutes les différences ne doivent pas apparaître comme prioritaires.

Le moteur doit hiérarchiser.

Une dimension peut devenir prioritaire lorsqu'elle combine :

-   importance élevée ;
-   écart élevé ;
-   score faible ;
-   réponses critiques ;
-   cohérence avec d'autres difficultés ;
-   impact potentiel sur la vie quotidienne.

------------------------------------------------------------------------

# 18. MATRICE DE PRIORISATION

Le moteur peut utiliser une matrice interne.

  Importance   Écart    Niveau de priorité
  ------------ -------- --------------------
  Faible       Faible   Faible
  Élevée       Faible   Modérée
  Faible       Élevé    Modérée
  Élevée       Élevé    Élevée

Cette matrice doit être enrichie par les autres données.

Elle ne constitue pas à elle seule le résultat final.

------------------------------------------------------------------------

# 19. SCORE DE COMPATIBILITÉ GLOBAL

Le score global ne doit pas être une simple moyenne des dimensions.

Il doit intégrer :

-   proximité entre partenaires ;
-   niveau des dimensions ;
-   importance des dimensions ;
-   ressources relationnelles ;
-   zones de vigilance.

Une architecture possible :

``` text
Score global
=
40 % proximité relationnelle
+
25 % ressources communes
+
20 % alignement sur sujets structurants
+
15 % capacité de fonctionnement relationnel
```

Les coefficients exacts doivent être validés après construction du
questionnaire.

Ces coefficients sont donc des **paramètres de conception**, pas des
valeurs définitives.

------------------------------------------------------------------------

# 20. NE PAS SURPONDÉRER UNE DIMENSION

Une seule dimension ne doit pas pouvoir faire passer automatiquement un
couple de :

> « bon profil »

à :

> « mauvais couple »

sauf si le questionnaire contient une règle de sécurité spécifique.

Les sujets critiques doivent être traités comme des **alertes
qualitatives**, pas simplement comme une pénalité mathématique.

------------------------------------------------------------------------

# 21. SCORE GLOBAL ET DIMENSIONS CRITIQUES

Exemple :

``` text
Score global = 74/100
```

Mais :

``` text
Communication = 72
Finances = 68
Projet familial = 76
Conflits = 65
Sécurité émotionnelle = 38
```

Le rapport ne doit pas dire :

> « Vous êtes compatibles à 74 %, donc tout va bien. »

Il doit dire :

> **« Votre bilan montre une base globalement favorable, mais la
> sécurité émotionnelle ressort comme un sujet qui mérite une attention
> particulière. Votre score global ne doit donc pas être lu isolément.
> »**

------------------------------------------------------------------------

# 22. RÈGLE DU « 15 % »

Un résultat faible doit être présenté avec une grande prudence.

Exemple :

``` text
Compatibilité globale = 15/100
```

Le système ne doit jamais écrire :

> « Vous êtes incompatibles. »

Il doit plutôt écrire :

> **« Vos réponses montrent actuellement peu de convergence sur
> plusieurs dimensions structurantes. Cela ne permet pas de conclure que
> votre relation est impossible. En revanche, cela indique que plusieurs
> sujets importants nécessitent des conversations approfondies et des
> accords explicites avant de tirer des conclusions sur la suite de
> votre relation. »**

Puis identifier précisément les dimensions concernées.

------------------------------------------------------------------------

# 23. SCORE FAIBLE = ZONE DE TRAVAIL

Le moteur doit suivre cette logique :

``` text
SCORE FAIBLE
≠
COUPLE IMPOSSIBLE
```

mais :

``` text
SCORE FAIBLE
→
SUJET À COMPRENDRE
→
SUJET À DISCUTER
→
SUJET À TRAVAILLER
```

------------------------------------------------------------------------

# 24. SCORE ÉLEVÉ = RESSOURCE

Inversement :

``` text
SCORE ÉLEVÉ
→
RESSOURCE À PRÉSERVER
```

Le rapport doit montrer au couple comment utiliser cette force pour
soutenir les autres domaines.

------------------------------------------------------------------------

# 25. PROFIL INDIVIDUEL

Chaque partenaire doit recevoir une lecture individuelle.

Exemple :

> **Votre manière de fonctionner dans la relation**

Puis une synthèse rédigée.

Le moteur doit expliquer :

-   forces ;
-   besoins ;
-   tendances ;
-   points de vigilance personnels ;
-   ressources ;
-   axes de développement.

Cette section doit être personnalisée.

------------------------------------------------------------------------

# 26. PROFIL DU COUPLE

Le moteur construit ensuite une lecture croisée.

Exemple :

> **Votre dynamique à deux**

Le texte doit expliquer :

-   ce qui crée de la stabilité ;
-   ce qui rapproche ;
-   ce qui peut provoquer des malentendus ;
-   les domaines dans lesquels les styles se complètent ;
-   les domaines dans lesquels un accord est nécessaire.

------------------------------------------------------------------------

# 27. TYPOLOGIE DES MATCHINGS

Le système peut classer les dimensions selon :

``` text
CONVERGENCE FORTE
CONVERGENCE FAVORABLE
COMPLÉMENTARITÉ
DIFFÉRENCE À CLARIFIER
DIVERGENCE SIGNIFICATIVE
ZONE DE VIGILANCE
```

Ces catégories sont internes.

Le rapport peut utiliser des formulations plus naturelles.

------------------------------------------------------------------------

# 28. EXEMPLE --- CONVERGENCE FORTE

``` text
A = 86
B = 84
```

Interprétation :

> Vos réponses montrent une forte proximité sur cette dimension. Vous
> semblez partager une compréhension similaire du sujet, ce qui peut
> constituer une ressource importante lorsque vous devez prendre des
> décisions ensemble.

------------------------------------------------------------------------

# 29. EXEMPLE --- DIFFÉRENCE À CLARIFIER

``` text
A = 82
B = 59
```

Interprétation :

> Vous semblez accorder tous les deux de l'importance à cette dimension,
> mais vos manières de la vivre diffèrent. Cette différence mérite
> d'être explorée afin que chacun comprenne ce que l'autre attend
> réellement.

------------------------------------------------------------------------

# 30. EXEMPLE --- DIVERGENCE SIGNIFICATIVE

``` text
A = 90
B = 38
```

Interprétation :

> Vos réponses montrent un écart important. Il ne signifie pas
> nécessairement que vos attentes sont incompatibles, mais il indique
> que vous pourriez vivre ce sujet de manière très différente au
> quotidien. Un accord explicite peut être particulièrement utile ici.

------------------------------------------------------------------------

# 31. EXEMPLE --- CONVERGENCE BASSE

``` text
A = 43
B = 46
```

Interprétation :

> Vous êtes relativement proches sur cette dimension, mais vos deux
> résultats indiquent qu'il s'agit actuellement d'un domaine qui
> pourrait bénéficier d'attention. Votre proximité peut justement
> devenir un avantage : vous pourriez travailler ensemble sur le même
> objectif.

------------------------------------------------------------------------

# 32. EXEMPLE --- COMPLÉMENTARITÉ

``` text
A = 84
B = 61
```

Le moteur doit vérifier si la différence est compatible avec les autres
résultats.

Il peut produire :

> Vous n'abordez pas ce sujet de la même manière. Cette différence peut
> parfois devenir une complémentarité, à condition que chacun
> reconnaisse la valeur de l'approche de l'autre et que vos
> responsabilités soient clairement définies.

------------------------------------------------------------------------

# 33. INDICE DE CONVERGENCE

Le moteur peut calculer un indice de proximité.

Formule de base :

``` text
Convergence = 100 - ABS(A - B)
```

Exemple :

``` text
A = 80
B = 75

Convergence = 95
```

Mais cet indice ne doit pas être utilisé seul.

------------------------------------------------------------------------

# 34. INDICE DE DIVERGENCE

``` text
Divergence = ABS(A - B)
```

Exemple :

``` text
A = 80
B = 45

Divergence = 35
```

Cet indice sert à identifier les sujets à examiner.

------------------------------------------------------------------------

# 35. INDICE DE RESSOURCE COMMUNE

Une dimension peut être considérée comme ressource lorsque :

``` text
A élevé
ET
B élevé
ET
écart faible
```

Exemple :

``` text
A = 82
B = 79
```

Le moteur peut produire :

> **Ressource commune forte**

------------------------------------------------------------------------

# 36. INDICE DE TRAVAIL COMMUN

Une dimension peut devenir une priorité commune lorsque :

``` text
A faible
ET
B faible
```

même si l'écart est faible.

Exemple :

``` text
A = 44
B = 41
```

Le rapport doit dire :

> Vous semblez partager la même difficulté sur cette dimension. Cela
> peut représenter une belle opportunité de travailler ensemble plutôt
> qu'un problème porté par une seule personne.

------------------------------------------------------------------------

# 37. INDICE DE BESOIN INDIVIDUEL

Une dimension peut nécessiter un travail individuel lorsqu'un partenaire
présente un score faible alors que l'autre présente un niveau élevé.

Exemple :

``` text
A = 35
B = 82
```

Le rapport doit éviter :

> « A est le problème. »

Préférer :

> **« Cette dimension semble représenter un besoin plus important pour
> vous actuellement. Il pourrait être utile d'explorer ce qui rend ce
> sujet plus difficile pour vous et ce dont vous auriez besoin pour vous
> sentir davantage en sécurité ou en confiance. »**

------------------------------------------------------------------------

# 38. INDICE DE TENSION POTENTIELLE

Une tension potentielle peut être identifiée lorsque :

``` text
écart élevé
+
importance élevée
+
dimension quotidienne
```

Exemples :

-   finances ;
-   enfants ;
-   famille ;
-   responsabilités ;
-   lieu de vie.

Ces sujets doivent recevoir une attention particulière.

------------------------------------------------------------------------

# 39. DIMENSIONS STRUCTURANTES

Certaines dimensions doivent avoir un poids contextuel plus important :

-   projet de vie ;
-   projet familial ;
-   valeurs ;
-   finances ;
-   engagement ;
-   sécurité relationnelle ;
-   gestion des conflits.

Mais le poids exact doit être validé méthodologiquement.

------------------------------------------------------------------------

# 40. DIMENSIONS DE FONCTIONNEMENT

D'autres dimensions décrivent davantage le fonctionnement quotidien :

-   communication ;
-   organisation ;
-   autonomie ;
-   responsabilités ;
-   affection ;
-   temps ensemble.

Elles doivent être analysées en relation avec les dimensions
structurantes.

------------------------------------------------------------------------

# 41. DIMENSIONS À RISQUE ÉLEVÉ

Certaines réponses doivent déclencher une **revue de sécurité**.

Par exemple, si le questionnaire contient des questions relatives à :

-   peur du partenaire ;
-   contrôle coercitif ;
-   violence ;
-   menaces ;
-   intimidation ;
-   isolement ;
-   contrainte ;
-   peur de répondre librement.

Le moteur doit pouvoir détecter un signal critique.

Il ne doit pas transformer automatiquement ce signal en score de
compatibilité.

------------------------------------------------------------------------

# 42. PRIORITÉ À LA SÉCURITÉ

Lorsqu'un signal sérieux apparaît :

``` text
SIGNAL DE SÉCURITÉ
        ↓
NE PAS COMPENSER PAR SCORE GLOBAL
        ↓
REVOIR L'INTERPRÉTATION
        ↓
AFFICHER UNE ORIENTATION APPROPRIÉE
```

Un couple ne doit jamais recevoir un message du type :

> « Vous avez 78 % de compatibilité malgré vos difficultés. »

si des réponses indiquent potentiellement une situation de danger.

------------------------------------------------------------------------

# 43. QUESTIONS SENSIBLES

Les questions sensibles doivent être conçues avec :

-   neutralité ;
-   clarté ;
-   possibilité de répondre sans pression ;
-   confidentialité ;
-   absence de jugement.

Le système doit éviter de présenter les réponses sensibles du partenaire
à l'autre sans règles explicites.

------------------------------------------------------------------------

# 44. LOGIQUE DU SCORE GLOBAL

Le score global peut être construit à partir de plusieurs indices.

Exemple de structure interne :

``` text
GLOBAL
│
├── Alignement
├── Convergence
├── Fonctionnement relationnel
├── Ressources
└── Vigilances
```

Le score final doit rester un indicateur synthétique.

------------------------------------------------------------------------

# 45. ÉVITER L'EFFET « NOTE SCOLAIRE »

Ne pas afficher :

> 15/100 = mauvais

> 95/100 = excellent

Le score doit être accompagné d'un libellé interprétatif.

Exemples :

> **15/100 --- Plusieurs différences structurantes à clarifier**

> **48/100 --- Des ressources présentes, avec plusieurs sujets
> importants à travailler**

> **72/100 --- Une base favorable avec des zones de vigilance**

> **88/100 --- Forte convergence sur de nombreuses dimensions, à
> préserver et approfondir**

Ces formulations sont des exemples de design et devront être calibrées
avec les seuils définitifs.

------------------------------------------------------------------------

# 46. ZONES DE SCORE

Le moteur peut utiliser des zones internes :

``` text
0–24
25–39
40–59
60–74
75–89
90–100
```

Mais les seuils définitifs doivent être validés après tests.

Il ne faut pas supposer qu'une frontière mathématique représente
automatiquement une réalité psychologique.

------------------------------------------------------------------------

# 47. SCORE = CONTEXTE

Le moteur doit toujours combiner :

``` text
score
+
écart
+
dimension
+
réponses
+
contexte
```

C'est cette combinaison qui produit une interprétation utile.

------------------------------------------------------------------------

# 48. PERSONNALISATION DU LANGAGE

Le moteur doit éviter de répéter :

> « Vos scores montrent... »

à chaque section.

Il doit varier naturellement :

> « Vos réponses suggèrent... »

> « Vous semblez partager... »

> « Une différence apparaît... »

> « Cette dimension ressort comme... »

> « Ce domaine semble constituer une ressource... »

------------------------------------------------------------------------

# 49. RÈGLE DE NON-DIAGNOSTIC

Le moteur ne doit pas poser :

-   diagnostic psychologique ;
-   diagnostic psychiatrique ;
-   diagnostic de personnalité clinique ;
-   diagnostic de trouble ;
-   diagnostic de violence sans protocole professionnel spécifique.

Il peut décrire des tendances relationnelles observées dans les
réponses.

------------------------------------------------------------------------

# 50. RÈGLE DE NON-PRÉDICTION

Le moteur ne doit pas prédire :

> « Vous allez divorcer. »

> « Vous allez rester ensemble. »

> « Votre mariage réussira à 82 %. »

Il peut dire :

> **« Vos réponses font ressortir plusieurs sujets qui méritent d'être
> clarifiés avant votre prochaine étape. »**

------------------------------------------------------------------------

# 51. RÈGLE DE RESPONSABILITÉ PARTAGÉE

Lorsque les résultats montrent une difficulté relationnelle, éviter de
désigner un coupable.

Éviter :

> « Votre partenaire communique mal. »

Préférer :

> **« Vos styles de communication semblent différents. Cette différence
> peut créer des malentendus lorsque l'un cherche à parler immédiatement
> et que l'autre a besoin de temps avant de répondre. »**

------------------------------------------------------------------------

# 52. RÈGLE DE RESPONSABILITÉ INDIVIDUELLE

Le moteur doit toutefois permettre à chacun de reconnaître sa part.

Exemple :

> **« Votre profil montre que vous avez tendance à vous retirer lorsque
> la tension monte. Cette stratégie peut vous aider à vous protéger à
> court terme, mais elle peut aussi laisser votre partenaire sans
> réponse. Une piste de travail consiste à apprendre à demander une
> pause tout en indiquant clairement quand vous reviendrez à la
> conversation. »**

La recommandation doit être concrète.

------------------------------------------------------------------------

# 53. RÈGLE DE RECOMMANDATION

Chaque zone prioritaire doit conduire à une action.

Structure :

``` text
OBSERVATION
↓
EXPLICATION
↓
IMPACT POSSIBLE
↓
OBJECTIF
↓
ACTION
↓
RESSOURCE
```

Le moteur ne doit pas simplement dire :

> « Travaillez votre communication. »

Il doit proposer une manière de commencer.

------------------------------------------------------------------------

# 54. EXEMPLE DE RECOMMANDATION

> **Votre priorité : mieux gérer les désaccords.**

> Vos réponses montrent que vous n'abordez pas les conflits de la même
> manière. Lorsque la tension augmente, l'un de vous semble chercher
> rapidement une solution tandis que l'autre a davantage besoin de
> recul.

> Cette différence peut créer un cercle dans lequel l'un insiste pour
> obtenir une réponse alors que l'autre se retire davantage.

> Pendant les deux prochaines semaines, essayez une règle simple :
> lorsque l'un demande une pause, il indique également le moment
> approximatif auquel la conversation reprendra.

> Exemple : « J'ai besoin de trente minutes pour me calmer. Je veux que
> nous reprenions cette conversation ce soir à 20 h. »

------------------------------------------------------------------------

# 55. PRIORITÉS MAXIMALES

Le rapport ne doit pas présenter quinze priorités.

Le moteur doit sélectionner les plus importantes.

Recommandation :

``` text
3 priorités principales
+
2 priorités secondaires maximum
```

La profondeur vaut mieux que l'accumulation.

------------------------------------------------------------------------

# 56. LIEN AVEC LES EXERCICES

Chaque priorité peut être associée à un exercice.

Exemple :

``` text
Priorité :
Communication

↓
Exercice :
« Ce que j'aimerais que tu comprennes »

↓
Plan d'action :
Conversation structurée 20 minutes
```

Le moteur doit pouvoir sélectionner l'exercice le plus pertinent.

------------------------------------------------------------------------

# 57. LIEN AVEC LES RESSOURCES

Même logique :

``` text
Priorité
↓
Exercice
↓
Ressource
↓
Accompagnement éventuel
```

Cela permet de construire une expérience personnalisée.

------------------------------------------------------------------------

# 58. ORDRE DES PRIORITÉS

Le moteur peut classer les sujets selon :

``` text
1. sécurité
2. sujets structurants
3. impact quotidien
4. écarts importants
5. difficultés récurrentes
6. opportunités de croissance
```

La sécurité prime toujours sur le score commercial ou esthétique.

------------------------------------------------------------------------

# 59. LOGIQUE DE MATCHING

Le terme « matching » ne doit pas être compris comme :

> trouver la personne parfaite.

Dans KELYA COUPLE, le matching signifie :

> **mettre en relation les réponses de deux personnes afin de comprendre
> leur niveau de convergence, leurs différences et leur dynamique
> potentielle sur plusieurs dimensions.**

------------------------------------------------------------------------

# 60. MATRICE DE MATCHING

Le moteur doit pouvoir construire une matrice :

  Dimension            A    B   Écart Nature              Priorité
  ----------------- ---- ---- ------- ------------------- ----------
  Communication       82   79       3 Convergence         Faible
  Finances            71   45      26 Différence          Élevée
  Projet familial     88   84       4 Convergence         Faible
  Familles            52   83      31 Divergence          Élevée
  Conflits            60   57       3 Convergence basse   Modérée

Cette matrice est interne au moteur.

Le rapport final peut en présenter une version simplifiée et élégante.

------------------------------------------------------------------------

# 61. MATRICE DES FORCES

Le moteur doit sélectionner les principales ressources.

Exemple :

``` text
1. Valeurs communes
2. Projet familial
3. Engagement
```

Puis expliquer pourquoi elles sont importantes.

------------------------------------------------------------------------

# 62. MATRICE DES DIFFÉRENCES

Sélectionner les différences qui méritent une conversation.

Exemple :

``` text
1. Finances
2. Familles
3. Besoin d'autonomie
```

------------------------------------------------------------------------

# 63. MATRICE DES PRIORITÉS

Enfin :

``` text
1. Gestion des conflits
2. Finances
3. Limites avec les familles
```

Cette matrice doit alimenter le plan d'action.

------------------------------------------------------------------------

# 64. RÈGLE DE COHÉRENCE

Une priorité affichée dans le résumé doit apparaître également dans :

-   l'analyse ;
-   la recommandation ;
-   l'exercice ;
-   le plan d'action ;

lorsqu'ils sont prévus par le niveau d'offre.

Le moteur ne doit pas dire en page 3 :

> « Finance = priorité n°1 »

puis ne plus jamais en parler.

------------------------------------------------------------------------

# 65. RÈGLE DE CONCLUSION

Chaque grande section du rapport doit se terminer par une conclusion.

Exemple :

> **En résumé, votre couple dispose d'une base commune solide sur ce
> sujet. Votre principal enjeu n'est pas de devenir identiques, mais de
> clarifier la manière dont vous souhaitez transformer cette vision
> commune en décisions concrètes.**

Les sections ne doivent pas se terminer brutalement après une liste de
scores.

------------------------------------------------------------------------

# 66. RÈGLE DE PROFONDEUR

Le moteur doit produire de vrais paragraphes.

Éviter :

``` text
Communication : 72
Force : écoute
Faiblesse : conflit
Action : parler davantage
```

Préférer plusieurs paragraphes expliquant :

-   ce que les réponses montrent ;
-   pourquoi cela compte ;
-   comment cela peut se manifester ;
-   ce que chacun peut faire ;
-   comment le couple peut avancer.

------------------------------------------------------------------------

# 67. RÈGLE DE STYLE

Le texte doit être :

-   humain ;
-   chaleureux ;
-   professionnel ;
-   nuancé ;
-   direct ;
-   concret.

Il ne doit pas ressembler à une fiche technique.

------------------------------------------------------------------------

# 68. PARAMÈTRES CONFIGURABLES

Le moteur doit séparer les règles du code.

Les paramètres doivent pouvoir être modifiés :

``` text
dimension_weights
score_thresholds
priority_thresholds
safety_rules
question_weights
reverse_scoring
profile_rules
report_rules
```

Ainsi, la méthodologie pourra être améliorée sans réécrire toute
l'application.

------------------------------------------------------------------------

# 69. VERSIONNAGE DU MOTEUR

Chaque rapport doit conserver la version du moteur qui l'a généré.

Exemple :

``` text
SCORING_ENGINE_VERSION = 1.0
```

Si les règles changent :

``` text
1.1
1.2
2.0
```

Les anciens rapports doivent rester traçables.

------------------------------------------------------------------------

# 70. REPRODUCTIBILITÉ

Pour les mêmes données et la même version du moteur, le système doit
pouvoir produire un résultat cohérent.

Les variations purement rédactionnelles peuvent être contrôlées par les
règles du moteur de génération.

------------------------------------------------------------------------

# 71. SÉPARATION SCORE / RÉDACTION

Le moteur de scoring ne doit pas écrire directement le rapport.

Architecture :

``` text
RÉPONSES
↓
SCORING ENGINE
↓
STRUCTURED RESULT
↓
REPORT ENGINE
↓
TEXTE FINAL
```

Cela permet de tester séparément :

-   la mathématique ;
-   l'interprétation ;
-   la rédaction.

------------------------------------------------------------------------

# 72. STRUCTURE DE SORTIE DU MOTEUR

Le moteur doit produire une structure exploitable.

Exemple conceptuel :

``` json
{
  "couple_id": "KLY-CPL-8F42Q",
  "engine_version": "1.0",
  "overall_score": 72,
  "dimensions": [],
  "strengths": [],
  "convergences": [],
  "differences": [],
  "watchpoints": [],
  "individual_priorities": [],
  "couple_priorities": [],
  "safety_flags": [],
  "recommended_exercises": [],
  "recommended_resources": []
}
```

Cette structure n'est pas le rapport.

C'est la matière première du moteur de génération.

------------------------------------------------------------------------

# 73. EXEMPLE DE DONNÉES DE SORTIE

``` json
{
  "dimension": "finances",
  "score_a": 74,
  "score_b": 46,
  "gap": 28,
  "classification": "significant_difference",
  "priority": "high",
  "interpretation_key": "financial_expectations_gap"
}
```

Le moteur de rapport utilise ensuite :

``` text
financial_expectations_gap
```

pour sélectionner le bon contenu rédactionnel.

------------------------------------------------------------------------

# 74. BIBLIOTHÈQUE D'INTERPRÉTATIONS

Il faut construire une bibliothèque interne de blocs d'interprétation.

Exemple :

``` text
communication_high_convergence
communication_low_convergence
communication_high_gap
finance_high_gap
finance_low_shared
family_high_gap
conflict_low_shared
```

Cette bibliothèque doit être riche.

Elle ne doit pas être limitée à quelques phrases.

------------------------------------------------------------------------

# 75. COMBINAISON DES BLOCS

Le moteur ne doit pas simplement empiler des blocs.

Il doit pouvoir combiner :

``` text
OBSERVATION
+
CONTEXTE
+
RELATION ENTRE DIMENSIONS
+
RECOMMANDATION
```

Exemple :

Une différence financière peut être reliée à une différence de vision du
projet familial.

Le moteur doit pouvoir identifier cette relation.

------------------------------------------------------------------------

# 76. INTERACTIONS ENTRE DIMENSIONS

Le moteur doit prévoir des règles d'interaction.

Exemple :

``` text
Finances faible
+
Projet familial faible
+
Communication faible
```

peut produire une priorité supérieure à celle de chaque dimension prise
séparément.

Cette logique doit être définie dans le moteur.

------------------------------------------------------------------------

# 77. EXEMPLE D'INTERACTION

Si :

``` text
Finances :
A = 80
B = 45

Communication :
A = 70
B = 40
```

le système peut identifier :

> différence financière + différence de communication

et recommander une conversation structurée plutôt qu'un simple exercice
sur l'argent.

------------------------------------------------------------------------

# 78. NE PAS SURINTERPRÉTER

Une corrélation entre deux résultats ne signifie pas automatiquement une
causalité.

Le moteur doit employer :

-   « peut contribuer » ;
-   « semble associé » ;
-   « peut se manifester » ;
-   « mérite d'être exploré ».

Éviter :

> « Votre faible score en communication provoque votre problème
> financier. »

------------------------------------------------------------------------

# 79. PRINCIPE D'INCERTITUDE

Lorsque les données ne permettent pas une conclusion claire, le moteur
doit le reconnaître.

Exemple :

> **Vos réponses ne permettent pas de déterminer clairement si cette
> différence constitue une difficulté réelle ou simplement une
> différence de préférence. Une conversation explicite vous aidera à le
> vérifier.**

Cette capacité à reconnaître l'incertitude renforce la qualité du bilan.

------------------------------------------------------------------------

# 80. PRINCIPE DE COMPLÉMENTARITÉ

Le moteur doit rechercher activement les différences qui peuvent être
complémentaires.

Exemple :

> Une personne planifie davantage et l'autre s'adapte plus facilement.

La conclusion peut être :

> Cette différence peut devenir une ressource si elle est reconnue et
> répartie volontairement.

------------------------------------------------------------------------

# 81. PRINCIPE DE FLEXIBILITÉ

Les profils ne doivent pas être présentés comme figés.

Éviter :

> « Vous êtes une personne évitante. »

Préférer :

> **« Vos réponses montrent une tendance à prendre davantage de recul
> lorsque la tension augmente. »**

------------------------------------------------------------------------

# 82. PRINCIPE DE RESPONSABILISATION

Le bilan doit aider chacun à agir.

Chaque partenaire doit pouvoir identifier :

``` text
Ce que je peux comprendre
Ce que je peux ajuster
Ce que je peux demander
Ce que je peux offrir
Ce que nous devons décider ensemble
```

------------------------------------------------------------------------

# 83. SCORE GLOBAL : PRÉSENTATION RECOMMANDÉE

Structure :

> **Votre compatibilité globale**

> **72/100**

> **Une base favorable, avec quelques sujets importants à clarifier.**

Puis :

> Ce résultat ne résume pas votre couple. Il synthétise les tendances
> observées dans les dimensions analysées. Les détails de votre bilan
> sont beaucoup plus importants que le chiffre lui-même.

------------------------------------------------------------------------

# 84. CAS D'UN SCORE TRÈS FAIBLE

Exemple :

> **Votre score global est de 28/100.**

Ne jamais écrire :

> « Votre couple est incompatible. »

Préférer :

> **« Vos réponses montrent actuellement des écarts importants sur
> plusieurs dimensions structurantes. Cela ne permet pas de conclure que
> votre relation est impossible. En revanche, il serait important de ne
> pas minimiser ces différences : elles méritent des conversations
> approfondies, des accords explicites et, si nécessaire, un
> accompagnement adapté. »**

------------------------------------------------------------------------

# 85. CAS D'UN SCORE ÉLEVÉ

Exemple :

> **Votre score global est de 88/100.**

Le système peut écrire :

> **« Votre bilan montre une forte convergence sur de nombreuses
> dimensions. Cette proximité constitue une ressource importante. Elle
> ne signifie cependant pas que vous n'aurez jamais de désaccords :
> votre enjeu sera aussi de préserver vos ressources lorsque les
> périodes plus exigeantes arriveront. »**

------------------------------------------------------------------------

# 86. CAS D'UN SCORE MOYEN

Exemple :

> **Votre score global est de 54/100.**

Le système peut écrire :

> **« Votre bilan montre un couple qui dispose de plusieurs points
> d'appui mais qui présente également des différences significatives.
> Votre résultat ne doit donc pas être lu comme un verdict, mais comme
> une invitation à identifier précisément les sujets qui demandent
> aujourd'hui le plus d'attention. »**

------------------------------------------------------------------------

# 87. RÈGLE SUR LA COMPARAISON DES PARTENAIRES

Ne jamais afficher une logique de classement :

> « Le meilleur des deux. »

> « Celui qui a le meilleur profil. »

> « Celui qui fait plus d'efforts. »

Les scores servent à comprendre la dynamique, pas à désigner un gagnant.

------------------------------------------------------------------------

# 88. RÈGLE SUR LE RESPONSABLE

Si un sujet apparaît surtout chez un partenaire, le rapport peut
identifier son axe individuel sans culpabiliser.

Exemple :

> **« Pour vous, ce domaine semble représenter un axe de progression
> plus important actuellement. »**

Puis :

> **« Pour votre partenaire, l'enjeu principal sera peut-être de
> comprendre ce besoin et de savoir comment vous soutenir sans prendre
> le problème à votre place. »**

------------------------------------------------------------------------

# 89. RÈGLE SUR LE TRAVAIL DU COUPLE

Pour chaque priorité commune, le système doit proposer :

1.  ce que vous observez ;
2.  pourquoi cela compte ;
3.  ce que chacun peut faire ;
4.  ce que vous devez décider ensemble ;
5.  un exercice ;
6.  une action concrète.

------------------------------------------------------------------------

# 90. RÈGLE DE FIN DU MATCHING

Le moteur ne doit jamais se terminer par :

> « Compatibilité : 67 %. »

Il doit produire :

``` text
SYNTHÈSE
+
FORCES
+
CONVERGENCES
+
DIFFÉRENCES
+
PRIORITÉS
+
ACTIONS
+
RESSOURCES
```

Le score est seulement une composante.

------------------------------------------------------------------------

# 91. TESTS DU MOTEUR

Avant mise en production, le moteur doit être testé sur des cas fictifs
très différents.

Au minimum :

### CAS A

Couple très convergent.

### CAS B

Couple très divergent.

### CAS C

Score global faible mais excellente communication.

### CAS D

Score global élevé mais zone de sécurité critique.

### CAS E

Deux partenaires faibles sur la même dimension.

### CAS F

Une personne très forte, l'autre faible.

### CAS G

Nombreuses différences mais forte capacité de réparation.

### CAS H

Couple très similaire mais faible fonctionnement relationnel.

### CAS I

Couple fiancé avec forte convergence sur le projet de vie.

### CAS J

Couple marié avec difficultés sur les finances et les familles.

Ces cas serviront de tests de non-régression.

------------------------------------------------------------------------

# 92. CAS DE TEST OBLIGATOIRE : « 15 % »

Créer explicitement un test automatisé dans lequel :

``` text
overall_score = 15
```

et vérifier que le rapport :

-   ne dit pas « incompatible » ;
-   ne dit pas « impossible » ;
-   ne prédit pas une rupture ;
-   identifie les dimensions responsables ;
-   propose des actions ;
-   reconnaît la nécessité éventuelle d'un accompagnement.

------------------------------------------------------------------------

# 93. CAS DE TEST OBLIGATOIRE : « 95 % »

Créer également un test :

``` text
overall_score = 95
```

et vérifier que le rapport :

-   ne promet pas une relation parfaite ;
-   rappelle que des différences peuvent apparaître ;
-   identifie les forces à préserver ;
-   propose éventuellement des pratiques de prévention.

------------------------------------------------------------------------

# 94. CAS DE TEST OBLIGATOIRE : SCORE MOYEN

Tester :

``` text
overall_score = 50
```

Le résultat doit être nuancé.

Il doit montrer que le couple possède à la fois :

-   des ressources ;
-   des différences ;
-   des axes de travail.

------------------------------------------------------------------------

# 95. VALIDATION HUMAINE

Avant publication du moteur, les cas de test doivent être relus par des
professionnels compétents dans le champ relationnel.

L'objectif est de vérifier :

-   pertinence ;
-   absence de jugement ;
-   absence de surinterprétation ;
-   qualité des recommandations ;
-   sécurité ;
-   cohérence.

------------------------------------------------------------------------

# 96. RÈGLE DE VERSIONNAGE MÉTHODOLOGIQUE

Toute modification importante du scoring doit entraîner :

-   changement de version ;
-   nouveaux tests ;
-   comparaison avec les anciens résultats ;
-   validation ;
-   documentation.

Ne jamais modifier silencieusement les coefficients en production.
